# Main server disk full — 2026-10-23

Server: main / production (`asem.aviconncorp.com`, `ip-172-31-9-28`), root disk 67 GB.
Times are UTC (IST = UTC + 5:30).

## Summary

| | Before (06:29) | After (06:44) |
| --- | --- | --- |
| Used / free | 67 GB / **479 MB (100 %)** | 42 GB / **26 GB (63 %)** |
| `/tmp/pg_backups` | 21 GB (12 dumps) | 6.0 GB (3 dumps) |
| `celerylogs1` current log | 4.3 GB | 0 (rotated to a 0.30 GB archive) |
| systemd journal | 2.4 GB | 480 MB |

Cause: the daily database backup script wrote a full dump to `/tmp/pg_backups` every day and
**never deleted it** (its clean-up line was commented out). Since 2026-10-13 each dump is 2.2 GB,
so the disk lost about 2.2 GB a day until it was full. A full disk then stopped the celery log
rotation, which made the queue-1 log grow to 4.3 GB in about two and a half days.

No database data, no S3 backup and no service configuration was lost or changed. All services
on main were running before and after.

## Root cause: the backup script

`crontab` of user `ubuntu`: `40 7 * * * /home/ubuntu/yashAws/db_backup.sh` (07:40 UTC = 13:10 IST).

The old script (dated 2026-02-09):

1. `pg_dump … | gzip > /tmp/pg_backups/warehouse_<date>.sql.gz`
2. `aws s3 cp` the file to the S3 bucket
3. clean-up: `#rm -f "$BACKUP_DIR/$FILENAME"` — **commented out**, so every local copy stayed.

Further problems found in it:

- **Failure checks did not work.** `if [ $? -ne 0 ]` after `pg_dump | gzip` tests only gzip, so a
  failed pg_dump went unnoticed; the "S3 upload failed" check tests the `echo` on the line before it,
  not the upload.
- **The main database password was in the script in plain text** (`export PGPASSWORD=…`). It was
  also shown once in a diagnostic session output on 2026-10-23. **Change this password.**
- No log: cron's output was not redirected anywhere.
- No free-space check: on a full disk it would still start a 2.2 GB dump.

### What the full disk already broke

- Celery log rotation (`/etc/logrotate.d/celery_logs`, `copytruncate` + `compress`) needs free space
  to copy and compress; after 2026-10-20 it could not finish, so
  `celerylogs1/celery_logs_of_server.log` reached 4.3 GB.
- Today's 07:40 backup would have failed (no room for another 2.2 GB).
- At 0 bytes free, PostgreSQL cannot write: consumption storage, alarms and the web app on main
  would start failing.

## What was changed (2026-10-23, with approval)

All steps on main; each preceded by a read-only check.

1. **Deleted the local dumps 10-15 … 10-20** — each one only after confirming the same file with
   the same size exists in S3. Kept 10-21 and 10-22. Freed 13 GB (829 MB → 15 GB free).
2. **Rotated `celerylogs1` once by hand** — with a one-off copy of only the `celerylogs1` block of
   `/etc/logrotate.d/celery_logs` and the normal state file, so `celerylogs2` (already rotated at
   00:00) was not touched. 4.3 GB → `celery_logs_of_server.log-20261023.gz` 0.30 GB in 127 s; logging
   continued in a fresh file. 15 GB → 24 GB free.
3. **Trimmed the systemd journal** — `journalctl --vacuum-size=500M`, freed 1.9 GB of archived
   journals. 24 GB → 26 GB free.
4. **Replaced the backup script** (see below), kept the old one, added a log file to its cron line,
   restarted `cron`.

Not done by us: between 06:29 and 06:38 the **10-11, 10-12 and 10-13 dumps were deleted by another
session** on main (another login was active, from 106.206.2.92 at 06:28). A plain `rm` leaves no log
entry, so who removed them is not known. **Those three were not in S3.**
At 06:59 the **10-14 dump (not in S3) and the 10-21 dump (in S3) were also gone**, again not by us;
only 10-22 was left. The 10-11 … 10-14 backups therefore no longer exist anywhere.

## The new backup script

Source: `deploy/main/db_backup.sh` (commit `4a4a4d58`), installed as
`/home/ubuntu/yashAws/db_backup.sh`. Same schedule; cron line now
`40 7 * * * /home/ubuntu/yashAws/db_backup.sh >> /home/ubuntu/yashAws/db_backup.log 2>&1`.

| | Old | New |
| --- | --- | --- |
| Where | `/tmp/pg_backups` | `/tmp/pg_backups` (unchanged, as requested) |
| Database login | `aviconn` with the password in the script | `postgres` system user via `sudo` (peer authentication) — **no password stored** |
| Local copies | never deleted | after a verified upload, older dumps are removed **only if the same file with the same size is in S3**; the newest one is kept |
| pg_dump failure | not detected | `set -euo pipefail` |
| Corrupt / partial dump | possible | written as `….partial`, `gzip -t` checked, then renamed |
| Upload check | tested the wrong command | `aws s3 cp` result **and** S3 size = local size |
| Disk full | starts anyway | refuses to start below 6 GB free |
| Two runs at once | possible | `flock` lock |
| Log | none | every step with a UTC timestamp in `yashAws/db_backup.log` |

Backups of the previous state on main (in `/home/ubuntu/yashAws/`):

- `db_backup.sh.old-2026-10-23` — the old script (mode 600; it still contains the password —
  delete it once the password is changed)
- `crontab.before-2026-10-23` — the crontab before the change

To roll back: `cp db_backup.sh.old-2026-10-23 db_backup.sh` and `crontab crontab.before-2026-10-23`.
